# Constellation

A codebase visualizer built with Next.js 16 (App Router), TypeScript, and Tailwind v4. Scans the repo, extracts top-level exported symbols via `ts-morph`, and renders the codebase as a WinDirStat-style squarified treemap — each file is a rectangle sized proportionally to its line count, nested inside its containing directory. Long-term goal: overlay live AI-agent activity (read/write badges, reasoning callouts) on top of the static map.

The visualizer scans `process.cwd()` by default and dogfoods itself — the home page renders this very repo. That means this CLAUDE.md is **also** part of the visualization. Keep it accurate: when the architecture, layout, or workflow changes, update this file in the same commit. See *Maintaining this file* below.

**Two-root architecture (sibling-clone install).** Constellation can be pointed at any target repo by setting the `CONSTELLATION_TARGET_ROOT` env var to an absolute path. There are two distinct directories:

- *Install root* — where Constellation's own code lives (`package.json`, `daemon/`, `lib/`, `app/`, `node_modules/`, `constellation.config.json`). Always equals `process.cwd()` for the supervisor and its child processes — the daemon and Next inherit cwd from `npm run dev`.
- *Target root* — the **default** repo being visualized (`.constellation/agents/`, `.claude/hooks/constellation/`, the source files that become tiles). Resolved via `resolveTargetRoot()` in `lib/config.ts`, which reads `CONSTELLATION_TARGET_ROOT` and falls back to `process.cwd()` (with a one-time stderr warning) when unset.

`loadConfig(installRoot)` reads from the install dir; `resolveStateDir(targetRoot)` joins onto the target. Single-repo dev (`npm run dev` in this repo, no env var) keeps working because both roots collapse to cwd.

**Multi-repo, multi-session.** A single running supervisor watches every repo whose hooks point at the daemon's port. The home page accepts `?repo=<absolute-path>` to switch which repo's tree is rendered, and `RepoSwitcher` (top-left chrome) lets the user arrow between repos that have at least one active Claude Code session. Inside the daemon, lifecycle state is namespaced by `(sessionId, agentId)` — two parallel sessions in the same repo each get their own `"main"` without colliding. Disk files follow the same scheme: `<sessionId>__<agentId>.json`.

## Current snapshot

As of the last update to this file:

- **Stack:** Next.js 16 (App Router) + React 19 + TypeScript 5.7 + Tailwind v4 (PostCSS plugin).
- **Runtime deps:** `ts-morph` (symbol extraction), `fast-glob` (file discovery), `zod` (lifecycle-file validation), `server-only` (guards server modules).
- **Dev deps that matter:** `tsx` (runs the daemon entry without a build step).
- **System deps:** `jq` (used by the hook curl shims to read the daemon port from config — `brew install jq` on macOS).
- **Single source of truth for runtime config:** `constellation.config.json` at the repo root holds the lifecycle-state directory, the daemon port, the visualizer port (`web.port`, default `47318`), the watched-tools list, and the agent-staleness TTL. TS callers read it via `lib/config.ts`; bash hooks read it via `.claude/hooks/lib/config.sh`. The watched-tools list still has to be hand-mirrored into `.claude/settings.json`'s `PreToolUse` matcher (Next.js settings JSON can't be templated), and the daemon logs a warning if the two diverge.
- **Source layout** (no `src/` — files live at the repo root):
  - `app/` — App Router entry. `page.tsx` is the home/visualizer route — server component that reads `?repo=<absolute-path>` from the URL, validates it (must exist on disk; falls back to `resolveTargetRoot()` otherwise), scans that repo, and fetches the daemon's `/repos` summary so the top-left switcher renders without a client roundtrip. `layout.tsx` + `globals.css` set up the shell. `api/agents/route.ts` proxies the daemon's `{ agents, repos }` snapshot (with disk fallback that derives repos from the agents' own `cwd` fields). `api/agents/stream/route.ts` pipes the daemon's SSE stream through to the browser. `dev/zoom-perf/` is a permanent dev-only perf bench (not linked from the home page) that renders a synthetic 5,000-tile tree through the same ref-driven transform pipeline production uses, so transform-stack regressions can be measured reproducibly across time.
  - `lib/` — server-side scanner + layout math + shared config/types/constants. `scan.ts` is now a thin orchestrator (~70 lines) that calls into pure phases under `lib/scan/`: `discover.ts` (file globbing + TS vs other split), `symbols.ts` (ts-morph exported declarations), `imports.ts` (project-internal import graph + reverse index), `descriptions.ts` (leading-comment extractors), `tree.ts` (FileNode assembly + directory tree + `countTree`), `synthetic.ts` (deterministic LCG-seeded 5,000-tile tree builder used only by `app/dev/zoom-perf/`). `treemap.ts` is a pure squarified-treemap function. `classify.ts` maps TS symbols to `SymbolKind`. `types.ts` is the shared shape, including a zod `ActiveAgentSchema` whose inferred type is the runtime contract for lifecycle files. `constants.ts` centralizes UI sizing/timing/tints — including the `ZOOM` group (`MIN`, `MAX`, `SENSITIVITY`, `LOD_COMMIT_QUANTUM`; the pan clamp is now strict no-overflow and takes no margin) and the shared `POINTER_MOVE_THRESHOLD` used by both Visualizer's gesture machine and PinController's empty-space-click guard. `config.ts` reads `constellation.config.json` (intentionally not `server-only` — the daemon imports it).
  - `daemon/` — the long-running TypeScript process that owns lifecycle state. `index.ts` is the entry; `lifecycle.ts` is the in-memory state machine (single writer, all mutations through one reducer; map keyed by `${sessionId}:${id}` so multi-session can't collide); `transcripts.ts` watches background and main JSONL transcripts (per-session keying — each session gets its own main watcher); `activity.ts` is the verbatim TS port of the old `lib/activity.sh` formatter; `server.ts` is a tiny built-in `http` server (no Express) exposing `/event/*`, `/agents`, `/agents/stream`, `/sessions`, `/repos`, `/health`; `sse.ts` broadcasts the `{ agents, repos }` payload to subscribers; `disk-sync.ts` debounces 50ms-per-(session,id) atomic writes; `atomic-write.ts` does the temp-file + rename and namespaces filenames as `<sessionId>__<id>.json`. The daemon listens on `127.0.0.1:<config.daemon.port>` (default 47317) and writes per-(session,id) JSON so the disk-fallback path keeps working.
  - `components/` — React components. `RepoSwitcher.tsx` is the top-left chrome (`"use client"`) showing the current repo name plus left/right arrows that `router.push('/?repo=…')` to cycle through repos with at least one active session; arrows are hidden when only the current repo is known. `Visualizer.tsx` is the gesture surface and the single writer of zoom/pan: it owns a `liveZoomPanRef` (live values, no React state) and a `committedZoom` React state that updates only on 5%-quantum LOD crossings; a single rAF tick mutates a `wrapperRef.current.style.transform` imperatively each frame, fires the `subscribeTransformChange` channel, and conditionally commits `committedZoom`. The wrapper is a child of the container and a *sibling* of `<HoverPanel>` so the panel's `position: fixed` resolves against the viewport rather than the transformed wrapper (CSS-Transforms makes a transformed ancestor a containing block for fixed descendants). All wheel + pointer + `f`-reset gestures live in one `useEffect` on the container/wrapper: scroll = cursor-anchored zoom, drag = pan, click ≤ 4 px = pin/unpin (migrated from TreemapNode's `onClick` so a press-and-drag pans), `f` = fit-to-viewport reset. `ZoomPanContext.tsx` exposes the read-only API (`committedZoom`, `getLive()`, `subscribeTransformChange(cb)`) plus the shared `clampPan` helper — `clampPan` is now strict no-overflow (`pan.x ∈ [viewportW * (1 − zoom), 0]`, symmetric for y), so the visualization always covers the viewport and the user never sees background bleed at the edges while panning. `LodContext.tsx` owns a global `minRender` value (default 8 px, range 4–64), persisted to `localStorage['constellation:lod-min-render']`, exposed via `useLod()`. `DetailSlider.tsx` is the header-mounted client component that drives it (right = more detail). `TreemapNode.tsx` is `React.memo`-wrapped (so non-LOD Visualizer re-renders skip the recursion) and recursively renders directories (squarify) and file tiles, with a *zoom-aware* gate `inner.{w,h} * committedZoom >= useLod().minRender` that progressively reveals smaller files as the user zooms in *and* lets the user retune for high-file-count repos like Parsley without recompiling. Description line-count stays in layout-px (text scales but the *number* of lines is constant; full zoom-aware line-count is deferred). FileTile reads hover/pin from `useHover()`, registers via `useRegisterTile(node.path)`, and uses a per-tile `floor(availH / DESCRIPTION_LINE_HEIGHT)` line-clamp so descriptions never clip mid-line. `AgentOverlay.tsx` is a thin orchestrator (~70 lines) that composes four hooks (`useAgentStream`, `useAgentLifecycle`, `useAgentPositions`, `useIdleClock`) and renders `<AgentIcon />` + `<AgentBubble />`. `AgentIcon` is intentionally click-transparent (no `pointer-events-auto`) so tile clicks beneath it still pin the underlying tile. `HoverPanel.tsx` is the cursor-anchored floating card showing the active file's description, exports, and import lists; in pin mode its position comes from PinController's per-frame re-anchor (live tile rect via `getBoundingClientRect()`); it's pointer-interactive (wheel scroll, text selection), viewport-clamped, resets `scrollTop` on file change without remounting, edge-touches the cursor in hover mode, keeps a 16 px offset in pin mode, and grows an always-visible × close button when pinned. `PinController.tsx` lives inside the providers and owns: Esc unpins; window-level click in empty space *outside* the visualizer container unpins (4 px pointer-distance guard, kept as a safety net since pointerup inside the container is now Visualizer's job); and the rAF re-anchor effect that subscribes to `subscribeTransformChange` and on every tick reads the pinned tile's current `getBoundingClientRect()` and feeds the new center back via `setPinned` — so the panel slides with the tile under live zoom + pan, and gets hidden (R13) when the tile is culled by LOD (`registry.get` returns null → `pinnedPos` becomes null → panel renders nothing while pin state persists). `data-path` is preserved as a redundant escape hatch *and* the positive-safelist marker that Visualizer's pointerup click resolver and PinController's empty-space click handler both walk via `closest()`. `data-hover-panel` and `data-agent-overlay` are sibling markers for the same purpose.
  - `hooks/` — frontend hooks. `useAgentStream.ts` (EventSource subscription with exponential-backoff reconnect, one-shot poll fallback during the backoff window), `useAgentLifecycle.ts` (mountedAt/removingAt fade tracking), `useAgentPositions.ts` (reads `TileRegistry`, recomputes on agent-list/registry/resize/scroll *and* every transform tick — so agent icons re-anchor under live zoom + pan via the `subscribeTransformChange` channel from `ZoomPanContext`), `useIdleClock.ts` (single setInterval re-render so `now - lastActiveAt` can be compared against `IDLE_DEBOUNCE_MS`).
  - `scripts/dev.mjs` — `npm run dev` runs this supervisor instead of `next dev` directly. It spawns `tsx daemon/index.ts` (idempotent: skipped if `.constellation/daemon.pid` points to a live process) and `next dev` side by side. Both spawn paths are idempotent: if the configured web port is already serving, the supervisor exits 0 with a "Constellation already running" message — that's how `install.sh` re-running inside a second repo is safe. Forwards stdio and shuts both down on Ctrl-C.
  - **What gets visualized.** Two filters: a *semantic* IGNORE list in `lib/scan/discover.ts` (skips `node_modules`, build output `.next`/`dist`/`out`/`build`, `.git`, runtime state `.constellation`/`.claude/worktrees`/`.claude/settings.local.json`, generated/binary files `*.tsbuildinfo`/`.DS_Store`/common image/font/archive extensions, `next-env.d.ts`, and `package-lock.json` — tracked in git but excluded here because at thousands of lines it would dwarf real source) and a *size-aware* gate using `SCAN_LIMITS` from `lib/constants.ts`. The gate stats every match: files above `MAX_FILE_BYTES` keep their tile but never get read (no source, no symbols), and directory subtrees above `MAX_DIR_BYTES` or `MAX_DIR_FILES` collapse to a single `__collapsed__` placeholder so a 14 GB build cache (Trigger.dev's `.trigger`, Turbo's `.turbo`, Cargo's `target`, etc.) shows up on the map without being loaded into memory. Everything else — TS, shell, markdown, JSON, CSS, configs, dotfiles like `.gitignore` and `.claude/settings.json` — becomes a tile.
  - **File descriptions.** Format → syntax: TS/JS/CSS via `/** … */` JSDoc; `.sh`/`.yaml`/`.yml`/`.rb` via leading `# …` block (after any shebang); `.py` via `"""…"""` module docstring (or `#` block fallback, after any `# coding:` line); `.sql` via `--` line block or `/* … */`; `.html`/`.htm` via `<!-- … -->` after any doctype; `.md` via the first paragraph below any heading. For TS/JS, the JSDoc may sit *above or below* a leading run of shebangs, string-literal directives (`'use client'`, `'use server'`, `'use strict'`, `'use asm'`), and a closed set of single-line directive comments (`// @vitest-environment`, `// @ts-nocheck`, `// eslint-disable …`, etc.) — so a Next.js `'use client'` file or a Vitest `// @vitest-environment node` test still gets its description rendered. New pragmas join the closed set in `lib/scan/descriptions.ts:LINE_DIRECTIVE_PATTERNS`; we don't use a wildcard `// @\w` rule because real-world `// @author` / `// @license` / `// @link` comments would silently consume real descriptions. Anything not in the dispatch table — most notably `.json`, lockfiles, `.gitignore` — shows just its filename, but each scanned repo can carry an optional `.constellation/descriptions.{yaml,yml,json}` sidecar that maps repo-relative paths to descriptions; sidecar entries always win over in-file extraction. Add a JSDoc/comment header to every new TS/JS/CSS/shell file — the extractor strips comment prefixes, drops anything from the first JSDoc tag onward, and returns the full body. Visual truncation happens display-side: tiles apply a per-tile `WebkitLineClamp` so the description never clips mid-line, and the hover panel scrolls long content. A scan-time cap forced both surfaces to share one shape, which broke long-description visibility (see `docs/solutions/ui-bugs/description-truncation-and-line-clamp-math-2026-04-30.md`). Don't write heuristic fallbacks; a wrong description is worse than none for the vibecoder this map is built for.
  - **`docs/`.** `brainstorms/` (origin requirements from `/ce:brainstorm`), `plans/` (implementation plans from `/ce:plan`), `solutions/` (institutional learnings from `/ce:compound`, organized by category with YAML frontmatter — `module`, `tags`, `problem_type`). Relevant when implementing or debugging in documented areas.
- **Live agent visibility:** project-scoped Claude Code hooks in `.claude/settings.json` POST events at the daemon, which owns all lifecycle writes. Hook scripts live in `.claude/hooks/` and are 3–5 line `curl` shims around `127.0.0.1:<port>/event/<name>` with a 500ms timeout and `|| true` — **daemon down ⇒ silent no-op ⇒ Claude Code session keeps working**. That invariant is the whole reason the bash system could be replaced.
  - Hook → daemon mapping: `agent-start.sh` → `/event/agent-start`, `agent-stop.sh` → `/event/agent-stop`, `agent-substop.sh` → `/event/subagent-stop`, `agent-touch.sh` → `/event/touch`, `agent-idle.sh` → `/event/idle`, `session-start.sh` → `/event/session-start`. Every shim `cat`s stdin into curl, so the Claude Code-supplied `session_id` and `cwd` ride on every event — the daemon refuses any event missing `session_id`. `session-start.sh` additionally `rm -f`s `${STATE_DIR}/${SESSION_ID}__*.json` (per-session, not the whole state dir) as belt-and-suspenders cleanup, so a crash in one session can't wipe another session's state.
  - `PreToolUse on Agent` (start): daemon creates an in-memory entry, sets `kind: "foreground"` or `"background"` from `tool_input.run_in_background`, schedules an atomic disk write of `<tool_use_id>.json` (or `_main.json` for the main agent — the underscore prefix is preserved purely for legacy fallback compatibility, since the daemon doesn't need it).
  - `PostToolUse on Agent` (stop): foreground spawns delete the entry. Background spawns stash the child's `agentId` from `tool_response.agentId` and leave the entry alone — `SubagentStop` cleans up later via `agentId` match. Background spawns also kick off a transcript watcher (`daemon/transcripts.ts:watchBackground`) that tails the JSONL at `tool_response.outputFile` and forwards tool_use entries into the lifecycle reducer; idle flips after 3s of no new tool_use.
  - `PreToolUse on Read|Edit|Write|MultiEdit|Bash|Grep|Glob|Task|WebFetch|WebSearch` (touch): daemon lazy-binds subagents (find by `agentId`, else find oldest unbound entry of matching `subagent_type`), upserts the main agent (id `"main"`), formats `currentActivity` via `daemon/activity.ts`, and (for file tools) sets `currentPath` relative to `cwd`. The first main-agent touch also kicks off `daemon/transcripts.ts:watchMain` so `currentMessage` (first sentence of the latest assistant text block) gets populated during text-generation stretches between tool calls.
  - `PostToolUse on the same set` and `Stop`: daemon flips `status: "idle"`. The entry is **not** removed — `currentPath` and `currentActivity` survive so the icon stays anchored and the bubble shows what just finished, just dimmed. The frontend debounces idle for 600ms to swallow between-tool flickers.
  - `SessionStart on startup|resume|clear`: daemon clears that session's in-memory state and disk-syncs the deletes; the shim also wipes only that session's `.constellation/agents/${SESSION_ID}__*.json` files directly. Other sessions in the same repo are left alone. (`compact` is excluded — it happens mid-session, where wiping would erase live state.)
  - **Why this isn't bash anymore:** the daemon is the single writer for every lifecycle field, so the old `agent-touch` / `agent-watch` / `agent-idle` clobber races are impossible by construction. Lazy-bind happens in-memory, so a foreground subagent that finishes before any tool call still cleans up correctly. Transcript watchers are managed by `Set<string>` membership in `daemon/transcripts.ts`, not pgrep.
  - **Frontend wiring:** `AgentOverlay` subscribes to `/api/agents/stream` (SSE) for sub-100ms updates and filters the snapshot's `agents` to those whose `cwd` matches the visualized `root` — so switching repos in the URL also switches which agents render. `useAgentStream` returns `{ agents, repos }`; `RepoSwitcher` reads `repos` from the same hook so the arrow list stays live. If the daemon is down, the SSE endpoint returns 503 and `useAgentStream` falls back to a one-shot `/api/agents` poll while it backs off and retries. `/api/agents` itself proxies the daemon when up and reads the on-disk JSON when not, deriving repo summaries from each agent's `cwd` field on the fallback path. React keys (and the position map) use a composite `${sessionId}:${id}` so two sessions with `id="main"` don't collide. Foreground subagents render as emerald letter icons with a thought-bubble; background subagents render in amber; the main agent renders as a sky dot, also with a bubble. Bubble text precedence: `currentActivity` → `currentMessage` → `description` → `subagent_type`. Idle agents dim to ~55% opacity in place (no teleport).
- **Scripts:** `npm run dev` (supervisor: spawns daemon + Next on `:47318`), `dev:next` (Next only on `:47318`, no daemon — useful when the user already has the daemon running), `daemon` (bare daemon entry on `:47317`), `build`, `start`, `lint`. No test runner yet.

## Working with this project

- Explaining the *why* behind suggestions, not just the *what*.

## Git — aggressive proactive management

The user has asked me to manage git proactively and aggressively. That means:

- **Commit often, in small logical units.** After any meaningful change (a feature works, a bug is fixed, a refactor is done), commit it without being asked. Don't batch unrelated changes into one commit.
- **Write good commit messages.** Format: short imperative subject (≤72 chars), blank line, then a body explaining the *why* if non-obvious. Reference what changed and why, not how.
- **Stage explicitly.** Use `git add <file>` over `git add -A` / `git add .` to avoid accidentally committing junk (`.env`, build artifacts, secrets).
- **Keep `.gitignore` healthy.** Add entries proactively when new tooling is introduced (node_modules, .venv, dist, .DS_Store, .env*, etc.).
- **Branch for non-trivial work.** Anything bigger than a small fix gets its own branch. Merge back to `main` when done.
- **Never force-push, never `reset --hard`, never `clean -fd` without confirming first.** Even when "managing aggressively," destructive ops always need a heads-up.
- **Push only when asked.** Local commits are free; pushes are visible. Don't `git push` without explicit confirmation.
- **Surface git state.** When starting a session, glance at `git status` / `git log` so I know what's in flight.
