# Constellation

A codebase visualizer built with Next.js 16 (App Router), TypeScript, and Tailwind v4. Scans the repo, extracts top-level exported symbols via `ts-morph`, and renders the codebase as a WinDirStat-style squarified treemap — each file is a rectangle sized proportionally to its line count, nested inside its containing directory. Long-term goal: overlay live AI-agent activity (read/write badges, reasoning callouts) on top of the static map.

The visualizer scans `process.cwd()` by default and dogfoods itself — the home page renders this very repo. That means this CLAUDE.md is **also** part of the visualization. Keep it accurate: when the architecture, layout, or workflow changes, update this file in the same commit. See *Maintaining this file* below.

**User-dir architecture.** Constellation has one canonical home on the user's machine: `~/.constellation/` (override via `CONSTELLATION_USER_DIR=<absolute-path>` for tests). Everything the daemon owns lives there:

- `~/.constellation/app/` — the installed Constellation code (when installed via the global installer).
- `~/.constellation/config.json` — runtime config (port, ttl, watched-tools), seeded on first daemon boot from the bundled `<install>/constellation.config.json`. Edits go to the user file; the bundled file is the default-source and is otherwise unread.
- `~/.constellation/repos.json` — registered repos: the persistent list the visualizer's switcher reads from, populated by `constellation add` (manual) and on-event `registry.touch()` (auto).
- `~/.constellation/state/agents/` — flat directory of every lifecycle file across every repo, named `<repoHash>__<sessionId>__<agentId>.json` so two repos can't collide on `"main"`.
- `~/.constellation/daemon.pid`, `~/.constellation/logs/daemon.log` — daemon process state.

There is no per-target `.constellation/` directory anymore. Helpers live in `lib/user-dirs.ts` (`userDir()`, `userConfigPath()`, `userStateDir()`, `userReposPath()`, `userPidPath()`, `userLogPath()`, `repoHash()`).

**Service lifecycle.** Constellation has two long-running pieces and on macOS each gets its own `launchctl` agent, both with `RunAtLoad: true` and `KeepAlive: true` so they survive reboots, logins, and kills:

- `~/Library/LaunchAgents/com.constellation.daemon.plist` runs `dist/daemon/index.js` (events + SSE on `daemon.port`, default 47317).
- `~/Library/LaunchAgents/com.constellation.web.plist` runs `scripts/web-server.mjs`, a small launcher that reads `~/.constellation/config.json` and execs `next start -p <web.port>` (default 47318) from the install dir. The launcher reads the port at process start, so port changes don't require a service reinstall — same pattern as the daemon.

`constellation service install` writes both plists (substituting `process.execPath`, the install root, and `CONSTELLATION_USER_DIR`) and verifies each tier's build artifact is present (`dist/daemon/index.js` and `.next/BUILD_ID`) before loading anything. `constellation start`/`stop`/`service uninstall` iterate over both. The web tier logs to `~/.constellation/logs/web.log` (separate from `daemon.log`) — `constellation logs --web` tails it. On Linux there's no launchd integration yet — users run `node dist/daemon/index.js` and `node scripts/web-server.mjs` under their own process manager. The dev supervisor (`scripts/dev.mjs`) is Constellation-self-dev only; end users don't run `npm run dev`.

**`constellation` CLI.** The user-facing entry point is `bin/constellation`, dispatching to `cli/<name>.mjs`. Subcommands: `add` (copies hook shims, runs the deterministic settings.json merge, POSTs `/repos/register`, then prompts to run `describe`, and auto-opens the dashboard before the long describe run so the user can watch tiles populate live; flags: `--no-describe` skips describe, `--yes`/`-y` runs non-interactively with sensible defaults, `--model haiku|sonnet|opus` pins the describe model. Agent-safe by construction: when `process.env.CLAUDECODE === "1"` (Claude Code's documented env var) or stdin isn't a real TTY, all interactive prompts are skipped and the auto-open is suppressed. The y/n prompt has a 30s wall-clock timeout fallback so a misclassified non-interactive run can't hang forever — `process.stdin.isTTY` lies inside Claude Code's pty-wrapped Bash tool), `rm` (POSTs `/repos/unregister`; `--purge` also removes hook shims), `list`/`ls`, `status` (probes both daemon `/health` and a TCP probe on the web port), `open` (browser to visualizer scoped to cwd), `describe` (spawns `claude --print --output-format stream-json --verbose` with a strict plain-English tone prompt — see `cli/description-tone.txt` — and writes `.constellation/descriptions.json` **incrementally per-file** as JSONL entries stream back, debounced 200ms-per-write. Each new description also fire-and-forgets a `POST /event/description-update` at the daemon, which fans it out via SSE to any connected browser tab — that's how tiles pop in live during onboarding. Skips files already covered; `--force` regenerates everything, `--yes` skips the confirm. Two watchdogs bound the spawned child: a 90s idle timeout (no stdout chunk for 90s ⇒ SIGTERM, then SIGKILL after a 5s grace) and a 15-min wall-clock ceiling — override via `CONSTELLATION_DESCRIBE_IDLE_MS` / `CONSTELLATION_DESCRIBE_TIMEOUT_MS`. Stderr is surfaced live below the spinner so a stuck child shows its diagnostic noise instead of going silent. End-of-run fallback parser recovers if streaming missed entries — e.g. Claude wrote the whole batch on one line or wrapped JSONL in a code fence), `start`/`stop` (load/unload both launchd agents), `service install`/`uninstall`, `logs [-f] [--web]` (daemon log by default, visualizer log with `--web`), `help`. JS-only on purpose — no compile step. Both the CLI and the daemon canonicalize repo paths via `realpathSync` so macOS's `/tmp` → `/private/tmp` symlink can't produce two registry entries for the same dir.

**Multi-repo, multi-session.** A single running daemon watches every repo whose hooks point at its port. The home page accepts `?repo=<absolute-path>` to switch which repo's tree is rendered, and `RepoSwitcher` (top-left chrome) lets the user arrow between repos — including idle git worktrees of the currently-viewing repo, so PR-review-style "swap to my feature branch worktree" lands without leaving the visualizer. The daemon's `/repos` endpoint joins the persistent registry with live agent counts; `/repos/active` is the lifecycle-derived view (only repos with at least one live agent). Inside the daemon, lifecycle state is namespaced by `(sessionId, agentId)` — two parallel sessions in the same repo each get their own `"main"` without colliding. The on-disk files add a `repoHash` prefix so two repos with the same `"main"` don't overwrite each other in the global state dir.

The wrapper is a child of the container and a *sibling* of `<HoverPanel>` so the panel's `position: fixed` resolves against the viewport rather than the transformed wrapper (CSS-Transforms makes a transformed ancestor a containing block for fixed descendants). Constellation-self-dev only — end users get the daemon under launchd via `constellation service install` and don't run this script. Forwards stdio and shuts both down on Ctrl-C.

  - **What gets visualized.** Two filters: a *semantic* IGNORE list in `lib/scan/discover.ts` (skips `node_modules`, build output `.next`/`dist`/`out`/`build`, `.git`, runtime state `.constellation`/`.claude/worktrees`/`.claude/settings.local.json`, generated/binary files `*.tsbuildinfo`/`.DS_Store`/common image/font/archive extensions, `next-env.d.ts`, and `package-lock.json` — tracked in git but excluded here because at thousands of lines it would dwarf real source) and a *size-aware* gate using `SCAN_LIMITS` from `lib/constants.ts`. The gate stats every match: files above `MAX_FILE_BYTES` keep their tile but never get read (no source, no symbols), and directory subtrees above `MAX_DIR_BYTES` or `MAX_DIR_FILES` collapse to a single `__collapsed__` placeholder so a 14 GB build cache (Trigger.dev's `.trigger`, Turbo's `.turbo`, Cargo's `target`, etc.) shows up on the map without being loaded into memory. Everything else — TS, shell, markdown, JSON, CSS, configs, dotfiles like `.gitignore` and `.claude/settings.json` — becomes a tile.
  - **File descriptions.** Two sources, sidecar wins. (1) **In-file extraction** — `lib/scan/descriptions.ts`: TS/JS/CSS via `/** … */` JSDoc; `.sh`/`.yaml`/`.yml`/`.rb` via leading `# …` block (after any shebang); `.py` via `"""…"""` module docstring (or `#` block fallback, after any `# coding:` line); `.sql` via `--` line block or `/* … */`; `.html`/`.htm` via `<!-- … -->` after any doctype; `.md` via the first paragraph below any heading. For TS/JS, the JSDoc may sit *above or below* a leading run of shebangs, string-literal directives (`'use client'`, `'use server'`, `'use strict'`, `'use asm'`), and a closed set of single-line directive comments (`// @vitest-environment`, `// @ts-nocheck`, `// eslint-disable …`, etc.) — so a Next.js `'use client'` file or a Vitest `// @vitest-environment node` test still gets its description rendered. New pragmas join the closed set in `lib/scan/descriptions.ts:LINE_DIRECTIVE_PATTERNS`; we don't use a wildcard `// @\w` rule because real-world `// @author` / `// @license` / `// @link` comments would silently consume real descriptions. Anything not in the dispatch table — most notably `.json`, lockfiles, `.gitignore` — shows just its filename. (2) **Generated sidecar** — `.constellation/descriptions.{yaml,yml,json}` maps repo-relative paths to descriptions; sidecar entries always win over in-file extraction. The sidecar is populated by `constellation describe`, **written incrementally during the run** — each `{path, description}` JSONL entry that streams back from Claude is debounce-flushed to the sidecar (200ms) and fire-and-forget POSTed at the daemon as a `description-update` event. The visualizer subscribes via `useDescriptionStream(root)` (SSE proxied through `/api/descriptions/stream`), and `LiveDescriptionsContext` resolves each tile's description with the live value winning over the server-rendered baseline; a `description-pop` CSS animation re-fires whenever the resolved value changes so tiles fade in as data lands. The sidecar is also self-maintained by the `description-refresh.sh` PostToolUse hook nudging the active agent on every edit. Tone is enforced by the shared prompt at `cli/description-tone.txt`: as short as it can be while still being clear (one sentence is usually enough; two or three short sentences when the file genuinely does several distinct things, never a full paragraph), no code words ("function"/"component"/etc. banned), aimed at a non-coder. Visual truncation happens display-side: tiles apply a per-tile `WebkitLineClamp` so the description never clips mid-line, and the hover panel scrolls long content. A scan-time cap forced both surfaces to share one shape, which broke long-description visibility (see `docs/solutions/ui-bugs/description-truncation-and-line-clamp-math-2026-04-30.md`). Don't write heuristic fallbacks; a wrong description is worse than none for the vibecoder this map is built for.
  - **`docs/`.** `brainstorms/` (origin requirements), `plans/` (implementation plans), `solutions/` (deep post-mortems with full root-cause analysis, organized by category with YAML frontmatter — `module`, `tags`, `problem_type`). Originally populated by the heavy `compound-engineering` plugin (`/ce:brainstorm`, `/ce:plan`, `/ce:compound`); that plugin is disabled in `.claude/settings.local.json` now and these dirs are read-only history. Per-PR insights get captured in the lighter `.constellation/learnings.json` sidecar instead — see *The compound loop* below. Still relevant when implementing or debugging in documented areas.
- **Live agent visibility:** project-scoped Claude Code hooks in `.claude/settings.json` POST events at the daemon, which owns all lifecycle writes. Hook scripts live in `.claude/hooks/` and are 3–5 line `curl` shims around `127.0.0.1:<port>/event/<name>` with a 500ms timeout and `|| true` — **daemon down ⇒ silent no-op ⇒ Claude Code session keeps working**. That invariant is the whole reason the bash system could be replaced. Two hooks do *not* talk to the daemon and run purely client-side: `description-refresh.sh` (PostToolUse on `Edit|Write|MultiEdit`) emits one `hookSpecificOutput.additionalContext` nudge with two prompts — update `.constellation/descriptions.json` if the edit changed what the file is for, and append to `.constellation/learnings.json` if the edit revealed a non-obvious insight worth remembering. Its sibling `learnings-surface.sh` (PreToolUse on the same matchers) is the recall side — it looks up `.constellation/learnings.json` for the file being edited, the immediate parent dir, and the `_general` fallback bucket, and injects matching insights as `additionalContext` so prior lessons land in Claude's context *before* the edit. See *The compound loop* below for the rationale.
  - Hook → daemon mapping: `agent-start.sh` → `/event/agent-start`, `agent-stop.sh` → `/event/agent-stop`, `agent-substop.sh` → `/event/subagent-stop`, `agent-touch.sh` → `/event/touch`, `agent-idle.sh` → `/event/idle`, `session-start.sh` → `/event/session-start`. Every shim `cat`s stdin into curl, so the Claude Code-supplied `session_id` and `cwd` ride on every event — the daemon refuses any event missing `session_id`. `lib/config.sh` reads `~/.constellation/config.json` (one source of truth for the port; `CONSTELLATION_USER_DIR` overrides for tests). `session-start.sh` additionally `rm -f`s `~/.constellation/state/agents/*__${SESSION_ID}__*.json` (per-session glob across every repo) as belt-and-suspenders cleanup, so a crash in one session can't wipe another session's state.
  - `PreToolUse on Agent` (start): daemon creates an in-memory entry, sets `kind: "foreground"` or `"background"` from `tool_input.run_in_background`, schedules an atomic disk write of `<tool_use_id>.json` (or `_main.json` for the main agent — the underscore prefix is preserved purely for legacy fallback compatibility, since the daemon doesn't need it).
  - `PostToolUse on Agent` (stop): foreground spawns delete the entry. Background spawns stash the child's `agentId` from `tool_response.agentId` and leave the entry alone — `SubagentStop` cleans up later via `agentId` match. Background spawns also kick off a transcript watcher (`daemon/transcripts.ts:watchBackground`) that tails the JSONL at `tool_response.outputFile` and forwards tool_use entries into the lifecycle reducer; idle flips after 3s of no new tool_use.
  - `PreToolUse on Read|Edit|Write|MultiEdit|Bash|Grep|Glob|Task|WebFetch|WebSearch` (touch): daemon lazy-binds subagents (find by `agentId`, else find oldest unbound entry of matching `subagent_type`), upserts the main agent (id `"main"`), formats `currentActivity` via `daemon/activity.ts`, and (for file tools) sets `currentPath` relative to `cwd`. The first main-agent touch also kicks off `daemon/transcripts.ts:watchMain` so `currentMessage` (first sentence of the latest assistant text block) gets populated during text-generation stretches between tool calls.
  - `PostToolUse on the same set` and `Stop`: daemon flips `status: "idle"`. The entry is **not** removed — `currentPath` and `currentActivity` survive so the icon stays anchored and the bubble shows what just finished, just dimmed. The frontend debounces idle for 600ms to swallow between-tool flickers.
  - `SessionStart on startup|resume|clear`: daemon clears that session's in-memory state and disk-syncs the deletes; the shim also wipes only that session's `~/.constellation/state/agents/*__${SESSION_ID}__*.json` files directly. Other sessions are left alone. (`compact` is excluded — it happens mid-session, where wiping would erase live state.)
  - **Why this isn't bash anymore:** the daemon is the single writer for every lifecycle field, so the old `agent-touch` / `agent-watch` / `agent-idle` clobber races are impossible by construction. Lazy-bind happens in-memory, so a foreground subagent that finishes before any tool call still cleans up correctly. Transcript watchers are managed by `Set<string>` membership in `daemon/transcripts.ts`, not pgrep.
  - **Frontend wiring:** `AgentOverlay` subscribes to `/api/agents/stream` (SSE) for sub-100ms updates and filters the snapshot's `agents` to those whose `cwd` matches the visualized `root` — so switching repos in the URL also switches which agents render. `useAgentStream` returns `{ agents, repos }`; `RepoSwitcher` reads `repos` from the same hook so the arrow list stays live. If the daemon is down, the SSE endpoint returns 503 and `useAgentStream` falls back to a one-shot `/api/agents` poll while it backs off and retries. `/api/agents` itself proxies the daemon when up and reads the on-disk JSON when not, deriving repo summaries from each agent's `cwd` field on the fallback path. React keys (and the position map) use a composite `${sessionId}:${id}` so two sessions with `id="main"` don't collide. Foreground subagents render as emerald letter icons with a thought-bubble; background subagents render in amber; the main agent renders as a sky dot, also with a bubble. Bubble text precedence: `currentActivity` → `currentMessage` → `description` → `subagent_type`. Idle agents dim to ~55% opacity in place (no teleport).

## The compound loop

Each PR teaches the system something durable, and the system surfaces what it already knows at the moment Claude is about to make a decision in the same area. The whole mechanism is two small bash hooks plus a path-keyed JSON sidecar:

- **Capture** — `.claude/hooks/description-refresh.sh` (PostToolUse on `Edit|Write|MultiEdit`). Emits one `additionalContext` payload with two prompts: update `.constellation/descriptions.json` if the edit changed what the file is for, **and** append a `{date, pr, insight}` entry to `.constellation/learnings.json` under the file-path key (or `_general` for cross-cutting insights) if the edit revealed something non-obvious — hidden constraint, foot-gun, reusable pattern, wrong-then-right judgment call. One sentence per insight, lead with the insight not the symptom. Skip mechanical edits.
- **Recall** — `.claude/hooks/learnings-surface.sh` (PreToolUse on `Edit|Write|MultiEdit`). Looks up `.constellation/learnings.json` for the file being edited, its immediate parent dir, and the most recent `_general` entries (cap of 3 per bucket, 9 total). If any match, injects them as `additionalContext` so Claude reads prior lessons *before* making the edit.
- **Storage** — `.constellation/learnings.json`. Path-keyed JSON, sibling of `descriptions.json`. Initial state is `{}`. Hooks create and grow entries; humans can read or prune freely.
- **Synthesis** — `.claude/agents/synthesize-app.md` is a Claude Code subagent (Opus + ultrathink, tools restricted to `Read, Write`) that reads only `.constellation/descriptions.json` — never the source — and writes a multi-paragraph plain-English interpretation of the whole project plus a `## Flagged surprises` bullet list to `.constellation/interpretation.md`. Invoke it via `/agents` or the `Agent` tool with `subagent_type: "synthesize-app"` whenever you want a reverse-engineering sanity check. If the synthesis reads wrongly, the descriptions are wrong, the code drifted, or both — and the flagged surprises name the specific files to look at first. Re-running overwrites cleanly, so diffing `interpretation.md` over time is a free architectural-drift detector.

The heavy `compound-engineering` plugin (`/ce:brainstorm`, `/ce:plan`, `/ce:compound`) is disabled in `.claude/settings.local.json` because this lighter loop replaces its day-to-day function. The 12-reviewer fan-out remains useful for rare deep-bug post-mortems; if you want one, re-enable the plugin temporarily and run `/ce:compound`. Files already in `docs/brainstorms/`, `docs/plans/`, `docs/solutions/` stay as frozen institutional history — not regenerated, still read.

## Git — aggressive proactive management

The user has asked me to manage git proactively and aggressively. That means:

- **Commit often, in small logical units.** After any meaningful change (a feature works, a bug is fixed, a refactor is done), commit it without being asked. Don't batch unrelated changes into one commit.
- **Write good commit messages.** Format: short imperative subject (≤72 chars), blank line, then a body explaining the *why* if non-obvious. Reference what changed and why, not how.
- **Stage explicitly.** Use `git add <file>` over `git add -A` / `git add .` to avoid accidentally committing junk (`.env`, build artifacts, secrets).
- **Keep `.gitignore` healthy.** Add entries proactively when new tooling is introduced (node_modules, .venv, dist, .DS_Store, .env*, etc.).
- **Branch for non-trivial work.** Anything bigger than a small fix gets its own branch. Merge back to `main` when done.
- **Never force-push, never `reset --hard`, never `clean -fd` without confirming first.** Even when "managing aggressively," destructive ops always need a heads-up.
- **Push only when asked.** Local commits are free; pushes are visible. Don't `git push` without explicit confirmation.
- **Surface git state.** When starting a session, glance at `git status` / `git log` so I know what's in flight.
